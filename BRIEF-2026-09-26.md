## 1. Mission

2b2t Museum imports historic 2b2t Minecraft base world-downloads into one
packed Mineclonia (Luanti) world at three Y-bands ("dimensions"):
overworld (dest_y_offset −61), End (−26880), Nether (−29072). Each base
import gets a "merge chunk" ring: generated Mineclonia terrain is blended
into the captured base's edges so seams are invisible and walkable
(`mods/spawnimport/gap_fill.lua` + `gap_field.lua`, built 2026-09-24).

**The owner's mandate for this round (verbatim):**

> "It seems like the algorithm we use for the overworld needs modification
> in the nether and the end, likely we need an entirely new algorithm for
> each dimension."

Plus a concrete nether ask: **do the fill, then re-generate the nether
roof over the fill chunks** (see §4.2 — with a caveat that must be
audited first), **lava must behave like overworld water** (match lake
beds and the lava surface), and a batch of correctness bugs (§3).

The full 205-base import will run **on the destination server**, not this
machine. This machine is the iteration rig: small fixtures, fast loops.

## 3. Confirmed bugs — fix these first (small, high value, verified)

### 3.1 Legacy block-id table: quartz ore imported as HOPPERS (and redstone block as quartz ore)

**Owner report:** "In some places there are literally thousands of hoppers.
17099, -28987.8, -7733.8 for example is part of a cluster of hoppers. I
think this might be a different thing... perhaps an ore."

**Verified root cause** — `lua_import/legacy.lua` lines 172–175:

```lua
blk(152, { default={name="minecraft:nether_quartz_ore"} }) -- seen
blk(153, { default={name="minecraft:hopper"} })            -- 16k seen!
for m, f in pairs(H_CHEST) do P[153][m] = {name="minecraft:hopper", props={facing=f}} end
P[153][0] = {name="minecraft:hopper", props={facing="down"}}
```

MC 1.12 ids are: **152 = redstone_block, 153 = nether_quartz_ore,
154 = hopper.** Evidence (Python oracle, full-chunk scans of Taylobase 4
DIM-1 and Hausemaster DIM-1):

- id 153: **16,497 instances, metadata always 0** — the ore signature
  (hoppers carry facing metadata 0–5; ores never do). The previous
  session's `-- 16k seen!` comment counted exactly these ore blocks and
  mislabeled them.
- id 154: **0 instances** — the real hopper never occurs in these captures.
- id 152: 13 instances, meta 0 (redstone block).
- Neighbors are correct: 155 = quartz_block ✓, 156 = quartz_stairs ✓.

**Fix:** replace those four lines with (keep the `H_CHEST` facing-table
pattern — it maps metas 2–5 to facing strings; hopper meta 0 = down, 1 = up):

```lua
blk(152, { default={name="minecraft:redstone_block"} })
blk(153, { default={name="minecraft:nether_quartz_ore"} })
blk(154, { default={name="minecraft:hopper", props={facing="down"}},
   [1]={name="minecraft:hopper", props={facing="up"}} })
for m, f in pairs(H_CHEST) do P[154][m] = {name="minecraft:hopper", props={facing=f}} end
```

Resolution paths already exist: `palette.lua:592` has a hopper handler
(`props.facing`, `props.enabled` → `mcl_hoppers:hopper[_side][_disabled]`);
`mc_to_mcl.json:207` maps `nether_quartz_ore → mcl_nether:quartz_ore`;
`:360` maps `redstone_block → mcl_redstone_torch:redstoneblock` (real
name, verified previously).

**Also audit the whole `legacy.lua` id table** against a canonical MC 1.12
id list + the corpus metadata distribution (same method as above) — one
mislabel was found by luck; there may be more. Then:
`luajit -bl lua_import/legacy.lua /dev/null` for syntax, run
`luajit mods/spawnimport/test_harness.lua` (expect ALL CHECKS — it decodes
real capture bytes), and verify the cluster at dest (17099, −28988, −7734)
now reads quartz ore (via the probe pattern, §7).

### 3.2 Mob spawners never activate (VoxelManip placement must call setup_spawner)

**Owner report:** "there is a spawner in Hausemaster's base, it's at 15346,
-29015, -7668 and it does not seem to be activating."

**Verified:** the capture has a real `minecraft:mob_spawner` TileEntity at
src (−263269, 58, 89012) with `SpawnData {id: "minecraft:blaze"}` — so the
capture is fine. Mineclonia's own source
(`~/dev/mineclonia/mods/ITEMS/mcl_mobspawners/init.lua`, at the
`register_node("mcl_mobspawners:spawner")` doc comment) states:

> "IF this node is placed by ANY other method (e.g. core.set_node,
> LuaVoxelManip), you MUST call mcl_mobspawners.setup_spawner right after
> the spawner has been placed."

Our placement path (`init.lua` `place_one_chunk`, VoxelManip write +
`needs_construct` repair loop at ~1062–1135) never calls it. The repair
loop currently handles containers (`on_construct`) and doors only.

**Fix direction:** in the block write loop, collect positions where
`bn[i] == "mcl_mobspawners:spawner"`; after the VoxelManip write, call
`mcl_mobspawners.setup_spawner(pos, mob)` for each (signature:
`setup_spawner(pos, Mob, _, _, MaxMobsInArea, PlayerDistance, _)` — see
`mcl_nether_fortresses/init.lua:25` for a real call site).
**The mob must come from the captured `SpawnData`** — `default_mob` is
`mobs_mc:pig`, which would be absurd in a nether base. Map
`SpawnData.id` (both `"minecraft:blaze"` and legacy bare `"Blaze"` styles
occur — normalize prefix/case) to `mobs_mc:<name>` via a small table
(blaze, zombie, skeleton, spider, cave_spider, slime, magma_cube,
zombie_pigman/zombified_piglin, witch, …). **Verify every mob name against
real registrations before writing it** (grep
`~/dev/mineclonia/mods/` for `mobs_mc:<name>` register calls; an earlier
grep of the mobs_mc directory layout came up empty due to a wrong path
guess — the names are unverified as of writing this brief). Fallback for
unknown ids: `setup_spawner(pos)` (default) or skip activation — decide
and document. TileEntities are available on the normalized chunk the same
way `anvil.decode_chunk_signs` reads them (`init.lua:1185`).

### 4.0 What is known so far (hypotheses — confirm before coding)

- `gap_fill.lua` is dimension-blind by design today: the ONLY
  dimension-aware piece is the `SEA` hack (`gap_fill.lua` ~528–540:
  `dy <= -20000` → `SEA = -31000`, "never classify any column as water" —
  which also means **lava is treated as plain terrain**). The overworld
  water rule (water columns: floor + water up to sea level, air above) has
  no lava analog.
- The merge's surface-skin shift + fill writer uses overworld-ish
  materials (`mcl_core:dirt_with_grass`, `mcl_core:stone` etc. — see the
  material classification lists at `gap_fill.lua` ~111–143). Finding #2's
  dirt/grass staircase below nether bedrock and #5's grass-to-void End
  merges look like those materials being dragged/filled dimension-blind.
  **Verify with the probe (§7) which writer path emits them.**
- The End band's *natural generated terrain* is suspicious in its own
  right: Endhaven audit warnings in `/tmp/full207f.log` (2026-09-25 run)
  show `mcl_core:dirt_with_grass` / `mcl_core:sand` at y≈−26816 in the End
  band — i.e. the ring terrain around End bases is overworld-looking
  mapgen output. Investigate what Mineclonia's mapgen actually generates
  at the End/Nether bands and what "natural" material the merge should
  blend to (end_stone; netherrack/nylium; lava seas).
- Nether roof (#6): a source-capture audit (Python oracle) of
  Hausemaster's DIM-1 at the spawner's chunk shows a FULL bedrock roof
  (y=127 solid bedrock, y=123–126 bedrock+netherrack mix). So at least
  there, the capture is intact and any missing roof in-world is **our
  pipeline** (strong suspect: gap_fill's floating-mass rejection / "floating
  junk → AIR" rule treating the roof as a floating mass over a gap; also
  check `place_one_chunk`'s "deterministic full chunk footprint" clear).
  **Required audit before implementing:** compare roof presence (bedrock
  rows at src y 122–127) in (a) source captures across many chunks above
  the base, (b) the deployed micro world at the same columns. That tells
  you whether roof regen applies to fill chunks only (owner's ask) or must
  also repair captured chunks (owner suspects Hausemaster himself broke
  parts of it — in that case captured data wins, do NOT overwrite it).
- Current audit output (per-base log line from `gap_fill.audit`) to keep
  green: `seam mismatches 0` (PASS-critical), `spilled base water 0`,
  `floating junk 0`. Known red flags right now: **floating junk 500
  (Taylobase) / 35,181 (Hausemaster)** in the nether — determine whether
  real junk or the overworld "floating" heuristic misfiring on nether
  roofs/caverns; **merge slopes over cap** large in nether (10,100, worst
  21) and End (100,138 on Endhaven trim, worst 13) — cliff seams beyond
  the ramp budget; tune only with owner consent (more terrain churn vs
  steeper steps).

### 4.1 Nether algorithm (design direction)

Per owner: fill first, then regenerate the nether roof over **fill chunks
only** (never captured chunks). Suggested shape:

1. **Materials:** fill/floor writes in the nether band use netherrack;
   surface skin = nylium (crimson/warped as the source biome dictates) or
   the sampled captured seam material; NEVER dirt/grass/stone.
2. **Lava:** treat like the overworld water rule — classify land vs lava
   columns against the nether lava sea level (MC nether lava sea = y 10/11
   → dest ≈ −29072+10; **verify the real level from capture data**),
   match lake beds and the lava surface at seams, don't slope-constrain
   into lava (see the existing "water edges are not slope-constrained"
   logic in `gap_field.lua` as template).
3. **Roof:** after the merge write, regenerate ceiling over fill chunks
   (bedrock plate + netherrack, matching the capture's roof height
   profile; the capture's roof blends at seams). Only in the domain chunks
   gap_fill wrote — the audit should gain a "roof integrity" check.
4. **Floor/void:** findings #1–#4 (stone columns below bedrock, dragged
   skins, abrupt walls) should disappear once materials + the height ramp
   are nether-aware; the "abrupt cut / single-block wall" (#4) may also
   need widening-budget tuning (`spawnimport_gap_max_step`,
   `MAX_EXTRA_RINGS`) or a steeper-but-continuous cliff rule (the audit's
   "natural relief" classification already keeps natural cliffs).

### 4.2 End algorithm (design direction)

Per owner: the End is fundamentally different (floating end-stone islands
over void) and likely wants its own merge. The single-surface height-field
model assumes continuous ground; End columns are islands over nothing.
Consider: per-column island detection (the `terrain_cols` floating-mass
rejection in `import_tools/placement_fit/source_footprint.lua` already
rejects thin masses over gaps — note Krobar's Interdimensional Bridge
capture profiles to ZERO land chunks for exactly this reason),
merge-to-nearest-island-edge rather than a continuous ramp, end_stone as
the only fill material, and no water/lava rule at all. The Endhaven
trim fixture (§6.2) is the test bed; finding #5's coordinate is the
flagship failure case.
